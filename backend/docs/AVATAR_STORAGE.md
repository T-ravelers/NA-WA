# 아바타 S3 저장 계약

이 문서는 프로필 사진 첨부(#444)를 구현할 때 백엔드와 운영 환경이 지켜야 할 S3 저장,
노출과 교체 규칙을 정의합니다. 실제 업로드 API와 저장 서비스는 아직 구현되지 않았으며,
이 문서와 `.env.example`은 구현 전에 계약만 고정합니다.

## 현재 상태와 구현 범위 구분하기

현재 `main`에는 정산 영수증용 `ReceiptStorageService`와 `AWS_S3_RECEIPT_BUCKET`만
연결돼 있습니다. `AWS_S3_AVATAR_BUCKET`은 아바타 기능을 위한 예약 변수이며
`application.properties`와 `S3Properties`는 아직 이 값을 읽지 않습니다.
`docker-compose.yml`도 백엔드 컨테이너에 이 값을 전달하지 않습니다. 기능 구현 PR에서
세 설정을 함께 연결해야 합니다.

이번 계약에는 다음 구현이 포함되지 않습니다.

- 프로필 사진 업로드·조회 API와 `AvatarStorageService`
- 아바타의 비추측성 식별자와 소유 회원·객체 키 매핑을 저장하는 변경
- 프로필 편집 화면의 파일 첨부 UI
- Google·LINE 프로필 사진을 다시 가져오는 시점 결정

## 객체 키는 서버가 정해진 접두사 안에서 만듭니다

아바타 객체 키는 다음 형식을 사용합니다.

```text
avatars/{memberId}/{UUID}.{jpg|png|webp}
```

- 클라이언트가 객체 키나 S3 주소를 정하지 않습니다.
- 접두사는 항상 `avatars/`입니다.
- 회원별 디렉터리에는 인증된 회원의 내부 `memberId`를 사용합니다.
- 파일을 올릴 때마다 새 UUID를 만듭니다. 원래 파일명은 객체 키에 넣지 않습니다.
- 확장자는 실제로 검증한 이미지 형식과 일치하는 `jpg`, `png`, `webp`만 허용합니다.
- 조회와 삭제 전에 객체 키가 `avatars/`로 시작하는지 다시 검증합니다.

## S3 권한과 공개 범위를 좁게 유지합니다

백엔드는 기존 영수증 저장소와 같은 AWS 리전 및 정적 자격증명을 사용하되 아바타용
버킷은 `AWS_S3_AVATAR_BUCKET`으로 따로 주입받습니다. IAM 권한은 `avatars/*`에 대한
다음 동작으로 제한합니다.

- `PutObject`
- `GetObject`
- `DeleteObject`

버킷의 퍼블릭 액세스 차단을 유지하고 공개 버킷 정책이나 CORS 규칙을 추가하지 않습니다.
브라우저에 S3 객체 주소나 프리사인 URL을 반환하지 않으며, 브라우저가 S3로 직접
업로드하지도 않습니다.

실제 버킷 이름, `AWS_ACCESS_KEY_ID`와 `AWS_SECRET_ACCESS_KEY` 값은 배포 환경의
`.env`에만 둡니다. 저장소와 Issue, PR, 로그에는 남기지 않습니다.

## 업로드와 조회는 백엔드를 통합니다

업로드는 프런트엔드가 백엔드 multipart API에 파일을 보내고 백엔드가 S3에
`PutObject`하는 방식으로 구현합니다. `SettlementReceiptController`의
`@RequestPart("file") MultipartFile` 처리와 `ReceiptStorageService`의 형식·크기 검증을
선례로 사용합니다.

업로드·교체·삭제는 인증된 회원이 자신의 아바타에 대해서만 수행할 수 있습니다. 반면
조회는 약속 참여자 목록·리뷰·회원 프로필·리포트 비교처럼 다른 회원의 사진을 표시해야
하므로 회원 소유권 검사와 분리합니다.

표시는 `GET /api/v1/avatars/{avatarId}`가 인증된 요청에 이미지 바이트를 스트리밍하는
방식으로 구현합니다. `{avatarId}`는 백엔드가 업로드마다 새로 생성한 UUID이며 `memberId`,
S3 객체 키나 순차 증가 값은 사용하지 않습니다. 프로필 이미지가 필요한 기존 API 응답은
S3 주소 대신 이 UUID를 포함한 백엔드 URL만 반환합니다. 따라서 인증된 회원은 자신에게
전달된 비추측성 URL로 다른 회원의 아바타를 표시할 수 있지만, 회원 ID를 바꿔 대입해서
사진을 열거할 수는 없습니다. 존재하지 않거나 교체로 폐기된 UUID는 `404`로 응답합니다.

응답은 실제 `Content-Type`, `X-Content-Type-Options: nosniff`와
`Cache-Control: private`을 포함해야 합니다. 프런트엔드와 백엔드는 같은 사이트의 운영
도메인을 사용하므로 브라우저는 이 백엔드 이미지 URL에 인증 쿠키를 실을 수 있습니다.

소셜 프로필 사진의 폴백 규칙은 API 구현 PR에서 확정합니다. 어떤 방식을 고르더라도
S3 주소를 프런트엔드 응답에 포함하지 않는 원칙은 유지합니다.

## 교체가 끝나면 이전 객체를 정리합니다

프로필 사진을 교체할 때는 새 객체와 새 `{avatarId}`로 교체를 완료한 뒤 이전 식별자를
조회 불가능하게 만들고 이전 아바타 객체 삭제를 시도합니다. 이전 객체 삭제가 실패해도
이미 완료된 프로필 변경 요청을 실패로 바꾸지 않고 경고 로그를 남깁니다. 로그에는
자격증명, 요청 본문이나 원본 파일명을 넣지 않습니다.

새 객체 업로드나 프로필 연결이 실패하면 기존 프로필 사진 참조를 유지해야 합니다.
객체와 DB 갱신의 정확한 보상 순서는 API 구현 PR에서 테스트와 함께 고정합니다.

## 구현 PR에서 검증할 항목

정적 빌드 성공만으로 교차 계정 S3 권한을 증명할 수 없습니다. 기능 구현 PR은 다음을
각각 검증하고 로컬 테스트와 실제 저장소 검증 결과를 구분해 기록해야 합니다.

- 객체 키가 지정한 회원과 `avatars/` 접두사를 벗어나지 않는지
- 허용한 이미지 형식만 업로드되는지
- 업로드·교체·삭제가 인증된 본인 아바타에만 적용되는지
- 인증되지 않은 조회는 거절하고, 인증된 사용자가 기존 API 응답으로 받은 다른 회원의
  비추측성 아바타 URL은 약속 참여자·리뷰·회원 프로필·리포트 비교 화면에서 표시되는지
- 회원 ID 대입으로 아바타를 열거할 수 없고 존재하지 않거나 폐기된 UUID는 `404`인지
- 새 사진으로 교체한 뒤 이전 객체 삭제가 시도되는지
- 삭제 실패가 성공한 프로필 변경을 되돌리지 않는지
- 실제 운영 권한과 같은 조건에서 `PutObject`, `GetObject`, `DeleteObject`가 동작하는지
- 퍼블릭 URL이나 프리사인 URL 없이 브라우저가 백엔드 경유 이미지를 표시하는지
