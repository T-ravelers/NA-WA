# 알림 API 계약

정산에서 일어난 일을 받는 사람 앞으로 한 줄씩 쌓아 두고, 화면이 그것을 읽어 가는 기능이다.
사용자가 정산 목록을 직접 열어 보기 전까지는 요청이 왔는지도 알 수 없었던 공백을 메운다.

즉시 알림(Web Push)은 여기에 없다. 이 문서가 다루는 적재·조회와 폴링은 Web Push를 도입한
뒤에도 그대로 필요하다 — 권한을 거부했거나 지원하지 않는 브라우저에는 이것만 남는다.

## API

| API | 용도 |
| --- | --- |
| `GET /api/v1/notifications` | 내 알림을 최신순으로 조회한다. |
| `GET /api/v1/notifications/unread-count` | 안 읽은 개수만 조회한다. 벨 배지가 쓴다. |
| `POST /api/v1/notifications/read-all` | 내 알림을 전부 읽음으로 바꾼다. |

셋 다 인증이 필요하고, 언제나 **요청한 본인의 알림만** 다룬다. 알림 번호를 경로에 받지
않으므로 남의 알림을 지목할 방법 자체가 없다.

### 목록 조회

`limit`을 선택적으로 받는다. 지정하지 않으면 30건, 100건을 넘겨 보내면 100건으로 맞춘다.
0이나 음수는 1건이 된다. **범위를 벗어난 값을 오류로 돌려주지 않는다** — 이 값은 화면의
목적을 바꾸지 않는다. 사용자는 "최근 알림"을 보고 싶을 뿐이라, 오류를 내면 화면만 비고
얻는 것이 없다.

```json
[
  {
    "id": 12,
    "type": "SETTLEMENT_REQUESTED",
    "settlementId": 90,
    "actorName": "Ari",
    "gatheringName": "Dinner",
    "amount": 30.0000,
    "currencyCode": "KRW",
    "readAt": null,
    "createdAt": "2026-08-21T12:00:00"
  }
]
```

시각 형식은 `yyyy-MM-dd'T'HH:mm:ss`이고 기준 시간대는 서버와 같은 `Asia/Seoul`이다.
`readAt`이 `null`이면 아직 안 읽은 알림이다.

`createdAt`과 `readAt`은 **둘 다 애플리케이션이 넘긴 값**이다. 컬럼 기본값
(`CURRENT_TIMESTAMP`)에 맡기지 않는 이유는 `createdAt`이 화면에 그대로 보이고 목록 정렬
기준이기도 해서다 — DB 시계를 쓰면 DB와 앱의 시간대가 어긋난 만큼 알림 시각이 통째로
밀린다. CI는 MySQL을 일부러 UTC로 띄워 이 의존을 드러낸다. 자세한 것은
[docs/TECH_STACK.md](../../docs/TECH_STACK.md).

### 읽음 처리

`POST /api/v1/notifications/read-all`은 `{ "updatedCount": 3 }`을 돌려준다. 이번 요청으로
실제로 읽음이 된 건수이며, 이미 다 읽었으면 0이다. 읽은 시각은 위의 `createdAt`과 같은
이유로 애플리케이션이 넘긴 값을 쓴다.

## 알림 종류와 받는 사람

| 타입 | 언제 | 받는 사람 | `amount`의 뜻 |
| --- | --- | --- | --- |
| `SETTLEMENT_REQUESTED` | 정산이 만들어졌을 때 | 아직 안 낸 구성원 전원 | 그 사람이 낼 몫 |
| `SETTLEMENT_PAID` | 구성원 한 명이 냈을 때 | 돈을 받을 원결제자 | 그 사람이 낸 금액 |
| `SETTLEMENT_COMPLETED` | 낼 사람이 모두 냈을 때 | 참여자 전원(원결제자 포함) | 정산 총액 |

원결제자는 자기 몫 행이 청구 대상이 아니라 구성원 목록에 들어 있지 않다. `COMPLETED`에서만
따로 넣어 준다 — 정산이 끝났다는 소식을 가장 기다린 사람이 빠지면 안 된다.

`actorName`은 `REQUESTED`와 `COMPLETED`에서 원결제자, `PAID`에서 방금 낸 사람이다.

## 표시용 값을 복사해 두는 이유

`actor_name`·`gathering_name`·`amount`·`currency_code`는 알림을 만들 때 그대로 복사해
저장한다. 매번 원본을 조인해 오지 않는다.

상대가 이름을 바꾸거나 정산이 지워져도 **그때 받은 알림은 받았던 그 문장 그대로 남아야
하기 때문이다.** 원본을 다시 읽으면 지난 알림의 내용이 소리 없이 바뀐다.

통화는 `settlements`에 없다. 정산의 근거가 된 원거래(`wallet_transfers.currency_code`)에서
가져온다. 이 조인이 빠지면 금액은 나오는데 단위가 사라진다.

## 언제 적재되는가

정산 서비스가 상태 전이 세 곳에서 도메인 이벤트를 발행하고,
`SettlementNotificationListener`가 `@TransactionalEventListener(AFTER_COMMIT)`으로 듣는다.

- **커밋된 뒤에만 듣는다.** 정산 트랜잭션이 도중에 되돌아가면 리스너는 아예 불리지 않는다.
  그렇지 않으면 실패한 지급에 대해 "누가 냈습니다" 알림이 남는다.
- **멱등 재시도에는 발행하지 않는다.** 같은 키로 다시 들어와 기존 결과를 그대로 돌려주는
  경로는 돈을 움직이지 않으므로 알릴 일도 없다. 재시도마다 알림이 쌓이면 안 된다.
- **완료 알림은 한 번만 나간다.** 완료로 바꾸는 `UPDATE`는 아직 `REQUESTED`인 정산만
  건드리므로, 마지막 지급이 동시에 여러 번 들어와도 한 번만 성공한다. 그 반환값이 1인
  경우에만 발행한다.
- **적재 실패는 로그만 남긴다.** 알림은 정산 상태에서 파생된 표시용 데이터다. 알림을 못
  적었다고 이미 오간 돈이 되돌아가서는 안 되므로 유실을 허용한다.

이벤트가 트랜잭션 밖에서 발행되면 리스너는 **아무 말 없이 안 불린다.** 발행 지점 세 곳이
모두 `@Transactional` 안에 있어야 하는 이유다.

## 화면이 언제 다시 물어보는가

벨 배지는 **15초마다** 안 읽은 개수를 다시 물어본다. 값은
`features/notification/model/notificationQueries.ts`의 `UNREAD_COUNT_POLL_INTERVAL_MS`다.

이 폴링은 탭이 백그라운드로 가면 멈춘다(TanStack Query의 `refetchIntervalInBackground`
기본값이 `false`다). 즉 사용자가 화면을 실제로 보고 있는 동안에만 도는데, 같은 자리에서
정산 요청을 주고받는 그 상황이 바로 빨리 와야 하는 상황이다. 요청 하나는 인덱스를 타는
개수 세기 한 번이다.

**백엔드 스케줄러의 60초를 그대로 가져오지 않는다.** 그 값은
[APPOINTMENT_DEPOSIT_STATE_MACHINE.md](APPOINTMENT_DEPOSIT_STATE_MACHINE.md) 15절이
"아무도 실시간으로 보고 있지 않은 쓰기 작업이라 주기가 길어도 된다"는 이유로 고른 것이라
전제가 정반대다.

이 쿼리에는 **`staleTime`을 두지 않는다.** 저장소의 다른 쿼리는 대부분 30초를 쓰지만,
여기에 붙이면 창 포커스 재조회가 그만큼 죽어서 앱으로 돌아와도 배지가 옛날 값으로 남는다.
체감의 대부분은 주기적 폴링이 아니라 "다시 열었을 때 바로 맞는가"에서 나온다.

개수가 **늘어난 순간**에만 정산 쿼리 캐시를 낡은 것으로 표시한다. 새 알림이 왔다는 것은 곧
정산 상태가 바뀌었다는 뜻이라, 벨 숫자만 올라가고 정산 화면이 옛날 값을 들고 있으면 사용자는
어느 쪽을 믿어야 할지 알 수 없다. 줄어드는 것은 사용자가 읽었다는 뜻이므로 건드리지 않는다.

## 아직 없는 것

알림 삭제, 개별 읽음 처리, 페이징, 정산 밖 도메인의 알림, 종류별 수신 설정. 필요해지면
후속 이슈로 다룬다.
