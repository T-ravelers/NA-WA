# 알림 API 계약

정산에서 일어난 일을 받는 사람 앞으로 한 줄씩 쌓아 두고, 화면이 그것을 읽어 가는 기능이다.
사용자가 정산 목록을 직접 열어 보기 전까지는 요청이 왔는지도 알 수 없었던 공백을 메운다.

즉시 알림(Web Push)은 이 알림 위에 얹힌다([웹 푸시](#웹-푸시)). 적재·조회와 폴링이 정본이고
푸시는 같은 알림을 기기로 바로 밀어 주는 덤이다 — 권한을 거부했거나 지원하지 않는
브라우저에는 목록과 폴링만 남는다.

정산 상태가 바뀔 때 적히는 알림 말고, 오래 내지 않은 구성원에게 서버가 시간이 지난 뒤 다시
알리는 **리마인더**도 같은 목록에 쌓인다([미납 리마인더](#미납-리마인더)).

## API

| API | 용도 | 성공 응답 |
| --- | --- | --- |
| `GET /api/v1/notifications` | 내 알림을 최신순으로 한 쪽씩 조회한다. | `200` |
| `GET /api/v1/notifications/unread-count` | 안 읽은 개수만 조회한다. 벨 배지가 쓴다. | `200` |
| `POST /api/v1/notifications/{id}/read` | 알림 하나를 읽음으로 바꾼다. | `204` |
| `POST /api/v1/notifications/read-all` | 내 알림을 전부 읽음으로 바꾼다. | `200` |
| `DELETE /api/v1/notifications/{id}` | 알림 하나를 지운다. | `204` |
| `DELETE /api/v1/notifications` | 내 알림을 전부 지운다. | `200` |

모두 인증이 필요하고, 언제나 **요청한 본인의 알림만** 다룬다.

읽음·지우기는 알림 번호를 경로로 받으므로 남의 번호를 적어 보낼 수는 있다. 막는 것은
**모든 UPDATE가 `recipient_member_id`로 범위를 좁힌다**는 점이다. 남의 번호나 없는 번호는
아무 행도 바꾸지 못하고 끝난다. 그리고 그때도 **응답은 성공과 똑같다** — 없는 번호에만
404를 주면 그 차이만으로 어떤 번호의 알림이 실제로 있는지 하나씩 알아낼 수 있다.

### 목록 조회

`limit`과 `cursor`를 선택적으로 받는다.

`limit`을 지정하지 않으면 30건, 100건을 넘겨 보내면 100건으로 맞춘다. 0이나 음수는 1건이
된다. **범위를 벗어난 값을 오류로 돌려주지 않는다** — 이 값은 화면의 목적을 바꾸지 않는다.
사용자는 "최근 알림"을 보고 싶을 뿐이라, 오류를 내면 화면만 비고 얻는 것이 없다.

`cursor`에는 직전 응답의 `nextCursor`를 그대로 돌려보낸다. 숫자가 아닌 값은 오류 대신 첫
쪽으로 떨어진다(`limit`과 같은 이유다).

**커서가 가리키는 행도 요청한 본인 것만 찾는다.** 남의 번호를 적어 보내면 없는 번호와
똑같이 빈 쪽이 나온다. 좁혀 두지 않으면 남의 알림 시각을 기준으로 내 목록이 잘려서, 잘린
모양만 보고도 그 알림이 언제쯤 생겼는지를 되짚을 수 있다.

```json
{
  "notifications": [
    {
      "id": 12,
      "type": "SETTLEMENT_REQUESTED",
      "settlementId": 90,
      "actorName": "Ari",
      "gatheringName": "Dinner",
      "amount": 30.0000,
      "currencyCode": "KRW",
      "readAt": null,
      "createdAt": "2026-08-21T12:00:00"
    }
  ],
  "nextCursor": "12"
}
```

`nextCursor`가 `null`이면 더 볼 것이 없다. 전체 개수는 싣지 않는다 — 그 숫자를 내려면 표를
매번 한 번 더 훑어야 하는데 화면이 쓰지 않는다.

**커서 비교는 알림 번호 하나가 아니라 `(created_at, notification_id)` 짝으로 한다.** 정렬
기준인 `created_at`은 DB가 아니라 앱이 넣는 값이라 번호 순서와 어긋날 수 있고, 번호만 보고
자르면 그 어긋난 만큼 어떤 알림은 어느 쪽에도 안 나오고 어떤 알림은 두 쪽에 걸쳐 나온다.
API가 주고받는 커서는 값 하나이고, 짝을 맞추는 일은 SQL 안에서만 일어난다.

시각 형식은 `yyyy-MM-dd'T'HH:mm:ss`이고 기준 시간대는 서버와 같은 `Asia/Seoul`이다.
`readAt`이 `null`이면 아직 안 읽은 알림이다.

`createdAt`과 `readAt`은 **둘 다 애플리케이션이 넘긴 값**이다. 컬럼 기본값
(`CURRENT_TIMESTAMP`)에 맡기지 않는 이유는 `createdAt`이 화면에 그대로 보이고 목록 정렬
기준이기도 해서다 — DB 시계를 쓰면 DB와 앱의 시간대가 어긋난 만큼 알림 시각이 통째로
밀린다. CI는 MySQL을 일부러 UTC로 띄워 이 의존을 드러낸다. 자세한 것은
[docs/TECH_STACK.md](../../docs/TECH_STACK.md).

### 읽음 처리

**화면에 들어온 것만으로는 읽음이 아니다.** 목록을 열었다고 전부 읽음으로 바꾸면 사용자는
무엇이 새로 왔는지 볼 기회를 잃고, 벨 숫자도 실제로 본 것과 무관하게 비워진다. 읽음은
알림을 눌렀을 때(`{id}/read`)와 "모두 읽음"을 눌렀을 때(`read-all`)만 일어난다.

`POST /api/v1/notifications/read-all`은 `{ "updatedCount": 3 }`을 돌려준다. 이번 요청으로
실제로 읽음이 된 건수이며, 이미 다 읽었으면 0이다.

`POST /api/v1/notifications/{id}/read`는 본문 없이 `204`다. 이미 읽었거나, 지웠거나, 남의
번호이거나, 없는 번호일 때도 모두 `204`다.

읽은 시각은 위의 `createdAt`과 같은 이유로 애플리케이션이 넘긴 값을 쓴다.

### 지우기

지우기는 행을 없애지 않고 `deleted_at`을 적는다(소프트 삭제). 조회 쿼리가 모두 이 컬럼을
걸러 내므로 화면에서는 사라지고, 무엇이 언제 지워졌는지는 남는다. 지운 시각도 읽은 시각과
같은 이유로 애플리케이션이 넘긴 값이다.

`DELETE /api/v1/notifications/{id}`는 `204`이고, 읽음과 같은 이유로 지울 것이 없을 때도
`204`다. `DELETE /api/v1/notifications`는 `{ "deletedCount": 3 }`을 돌려준다.

이미 받아 둔 쪽의 마지막 알림을 지운 뒤에도 그 번호를 커서로 쓸 수 있다. 커서가 가리키는
행을 찾을 때는 `deleted_at`을 보지 않기 때문이다 — 그렇지 않으면 카드 하나를 지운 순간
"더 보기"가 끊긴다.

## 알림 종류와 받는 사람

| 타입 | 언제 | 받는 사람 | `amount`의 뜻 |
| --- | --- | --- | --- |
| `SETTLEMENT_REQUESTED` | 정산이 만들어졌을 때 | 아직 안 낸 구성원 전원 | 그 사람이 낼 몫 |
| `SETTLEMENT_PAID` | 구성원 한 명이 냈을 때 | 돈을 받을 원결제자 | 그 사람이 낸 금액 |
| `SETTLEMENT_COMPLETED` | 낼 사람이 모두 냈을 때 | 참여자 전원(원결제자 포함) | 정산 총액 |

원결제자는 자기 몫 행이 청구 대상이 아니라 구성원 목록에 들어 있지 않다. `COMPLETED`에서만
따로 넣어 준다 — 정산이 끝났다는 소식을 가장 기다린 사람이 빠지면 안 된다.

`actorName`은 `REQUESTED`와 `COMPLETED`에서 원결제자, `PAID`에서 방금 낸 사람이다.

## 표시용 값을 복사해 두는 이유

`actor_name`·`gathering_name`·`amount`·`currency_code`는 알림을 만들 때 그대로 복사해
저장한다. 매번 원본을 조인해 오지 않는다.

상대가 이름을 바꾸거나 정산이 지워져도 **그때 받은 알림은 받았던 그 문장 그대로 남아야
하기 때문이다.** 원본을 다시 읽으면 지난 알림의 내용이 소리 없이 바뀐다.

통화는 `settlements`에 없다. 정산의 근거가 된 원거래(`wallet_transfers.currency_code`)에서
가져온다. 이 조인이 빠지면 금액은 나오는데 단위가 사라진다.

## 언제 적재되는가

정산 서비스가 상태 전이 세 곳에서 도메인 이벤트를 발행하고,
`SettlementNotificationListener`가 `@TransactionalEventListener(AFTER_COMMIT)`으로 듣는다.

- **커밋된 뒤에만 듣는다.** 정산 트랜잭션이 도중에 되돌아가면 리스너는 아예 불리지 않는다.
  그렇지 않으면 실패한 지급에 대해 "누가 냈습니다" 알림이 남는다.
- **멱등 재시도에는 발행하지 않는다.** 같은 키로 다시 들어와 기존 결과를 그대로 돌려주는
  경로는 돈을 움직이지 않으므로 알릴 일도 없다. 재시도마다 알림이 쌓이면 안 된다.
- **완료 알림은 한 번만 나간다.** 완료로 바꾸는 `UPDATE`는 아직 `REQUESTED`인 정산만
  건드리므로, 마지막 지급이 동시에 여러 번 들어와도 한 번만 성공한다. 그 반환값이 1인
  경우에만 발행한다.
- **적재 실패는 로그만 남긴다.** 알림은 정산 상태에서 파생된 표시용 데이터다. 알림을 못
  적었다고 이미 오간 돈이 되돌아가서는 안 되므로 유실을 허용한다.

이벤트가 트랜잭션 밖에서 발행되면 리스너는 **아무 말 없이 안 불린다.** 발행 지점 세 곳이
모두 `@Transactional` 안에 있어야 하는 이유다.

## 화면이 언제 다시 물어보는가

벨 배지는 **15초마다** 안 읽은 개수를 다시 물어본다. 값은
`features/notification/model/notificationQueries.ts`의 `UNREAD_COUNT_POLL_INTERVAL_MS`다.

이 폴링은 탭이 백그라운드로 가면 멈춘다(TanStack Query의 `refetchIntervalInBackground`
기본값이 `false`다). 즉 사용자가 화면을 실제로 보고 있는 동안에만 도는데, 같은 자리에서
정산 요청을 주고받는 그 상황이 바로 빨리 와야 하는 상황이다. 요청 하나는 인덱스를 타는
개수 세기 한 번이다.

**백엔드 스케줄러의 60초를 그대로 가져오지 않는다.** 그 값은
[APPOINTMENT_DEPOSIT_STATE_MACHINE.md](APPOINTMENT_DEPOSIT_STATE_MACHINE.md) 15절이
"아무도 실시간으로 보고 있지 않은 쓰기 작업이라 주기가 길어도 된다"는 이유로 고른 것이라
전제가 정반대다.

이 쿼리에는 **`staleTime`을 두지 않는다.** 저장소의 다른 쿼리는 대부분 30초를 쓰지만,
여기에 붙이면 창 포커스 재조회가 그만큼 죽어서 앱으로 돌아와도 배지가 옛날 값으로 남는다.
체감의 대부분은 주기적 폴링이 아니라 "다시 열었을 때 바로 맞는가"에서 나온다.

개수가 **늘어난 순간**에만 정산 쿼리 캐시를 낡은 것으로 표시한다. 새 알림이 왔다는 것은 곧
정산 상태가 바뀌었다는 뜻이라, 벨 숫자만 올라가고 정산 화면이 옛날 값을 들고 있으면 사용자는
어느 쪽을 믿어야 할지 알 수 없다. 줄어드는 것은 사용자가 읽었다는 뜻이므로 건드리지 않는다.

## 웹 푸시

알림이 적재되면 같은 알림을 받는 사람의 기기들로 웹 푸시도 보낸다. **푸시는 목록을 대신하지
않는다.** 권한을 거부했거나 브라우저가 지원하지 않으면 목록과 폴링만 남고, 푸시를 놓쳐도
폴링이 메운다.

### 구독 API

| API | 용도 | 성공 응답 |
| --- | --- | --- |
| `GET /api/v1/push-subscriptions/public-key` | 구독에 쓸 VAPID 공개키를 조회한다. 푸시가 꺼져 있으면 `publicKey`가 `null`이다. | `200` |
| `PUT /api/v1/push-subscriptions` | 이 기기를 등록한다. | `204` |
| `DELETE /api/v1/push-subscriptions` | 이 기기를 해지한다. 본문은 `{ "endpoint": "..." }`다. | `204` |

모두 인증이 필요하다.

**공개키는 API로 내려준다.** 프론트엔드(Vercel)와 백엔드(EC2) 두 곳의 환경 변수가 어긋나면
구독은 되는데 푸시가 한 건도 도착하지 않는다. 키를 한 곳에서만 들고 있으면 그럴 수 없다.

```json
{
  "endpoint": "https://fcm.googleapis.com/fcm/send/...",
  "p256dh": "BP...",
  "auth": "k8...",
  "language": "ja"
}
```

- `p256dh`·`auth`는 브라우저 `PushSubscription.toJSON().keys`의 base64url 값 그대로다.
  풀었을 때 각각 65바이트(`0x04`로 시작하는 압축하지 않은 P-256 점)와 16바이트여야 한다.
- `language`는 `en`·`ja`·`zh-TW`·`vi` 중 하나다(대소문자 무시, 비우면 `en`). 서버에는 알림
  문구를 만드는 i18n이 없어서 이 값을 푸시 본문에 실어 보내고, 문구는 서비스 워커가 알림
  목록과 같은 번역 파일로 만든다. 그 밖의 값은 `400`(`COMMON-001`)이다.
- 어느 필드든 형식이 틀리면 `400`(`COMMON-001`)이다.

**같은 `endpoint`는 하나뿐이다(UNIQUE).** 같은 기기를 다시 등록하면 키와 언어를 갱신하고,
다른 계정이 같은 기기로 등록하면 소유자를 그 계정으로 옮긴다. 그러지 않으면 이전 계정의
알림이 지금 그 기기를 쓰는 사람에게 계속 도착한다. 한 회원은 기기마다 구독을 하나씩 가진다.

해지는 **회원과 `endpoint`가 모두 맞는 행만** 지운다. `endpoint`는 남이 알 수도 있는 값이라
회원으로 좁히지 않으면 남의 기기를 해지할 수 있다. 없거나 남의 `endpoint`여도 `204`다 —
읽음·지우기와 같은 이유로, 응답이 갈리면 그 차이가 "그 주소의 구독이 있다"는 사실을 알려 준다.

**`endpoint`는 서버가 직접 POST하는 주소다.** 사용자가 적어 보낸 값을 그대로 받으면 서버가
임의의 주소로 요청을 보내게 되므로(SSRF), `https`이면서 아래 도메인(또는 그 하위)일 때만
받고 512자를 넘으면 받지 않는다. 그 밖은 `400`이다.

| 도메인 | 푸시 서비스 |
| --- | --- |
| `fcm.googleapis.com` | Chrome 등 Chromium 계열 |
| `push.services.mozilla.com` | Firefox |
| `push.apple.com` | Safari·iOS 홈 화면 앱 |
| `notify.windows.com` | Edge의 Windows 푸시. 공식 문서로는 확인하지 못했다 |

목록이 낡으면 새 브라우저의 구독이 `400`으로 막힌다. 조용히 사라지지 않고 구독 요청에서
바로 드러나므로, 그때 `PushSubscriptionServiceImpl.PUSH_SERVICE_DOMAINS`에 도메인을 더한다.

### 보내기

```text
정산 이벤트 → Listener(AFTER_COMMIT) → Recorder(자기 트랜잭션에서 적재) → 적재한 알림
           → PushSender(전용 스레드풀) → 수신자의 기기마다 푸시 서비스로 POST
```

- 적재가 실패하면 보낼 알림이 없으니 푸시도 나가지 않는다. 푸시가 실패해도 이미 적힌 알림과
  정산에는 영향이 없다. `PushSender`는 예외를 밖으로 던지지 않는다.
- **최선 노력이다.** 재시도하지 않는다. 전용 풀(스레드 4개, 대기열 200)이 가득 차면 새
  작업을 버리고 로그만 남긴다. 호출한 스레드에서 실행하면 밀린 푸시 때문에 정산 요청이
  느려지고, 예외로 알리면 푸시 때문에 정산·알림 처리가 실패하기 때문이다.
- 본문은 `aes128gcm`(RFC 8291)으로 암호화하고 VAPID(RFC 8292)로 서명한다. 푸시 서비스가 기기를
  기다려 주는 시간(TTL)은 24시간이고, 요청마다 5초 안에 응답이 없으면 포기한다.
- 푸시 서비스가 `404`·`410`으로 답하면 끝난 구독(앱 삭제·권한 회수·만료)이므로 지운다. 그 밖의
  실패(`429`, `5xx` 등)는 일시적일 수 있어 구독을 그대로 둔다.
- 기기 하나의 실패가 같은 회원의 다른 기기로 번지지 않는다.
- 로그에는 구독 번호와 상태 코드, 예외 종류만 남긴다. `endpoint` 경로는 그 기기로 보낼
  권한을 가리키는 값이라 남기지 않는다.

푸시 본문은 문장이 아니라 값이다. 알림 목록 응답에서 `id`·`readAt`·`createdAt`을 빼고
`language`를 더한 모양이다.

```json
{
  "type": "SETTLEMENT_REQUESTED",
  "settlementId": 90,
  "actorName": "Ari",
  "gatheringName": "Dinner",
  "amount": 30.0000,
  "currencyCode": "KRW",
  "language": "ja"
}
```

**푸시를 눌러도 읽음 처리하지 않는다.** 화면에 들어온 것만으로는 읽음이 아니라는 위의 규칙
그대로다. 누르면 해당 정산 상세로 이동할 뿐이고, 읽음은 알림 목록에서 항목을 눌렀을 때만
일어난다.

### 설정

| 환경 변수 | 설명 |
| --- | --- |
| `VAPID_PUBLIC_KEY`·`VAPID_PRIVATE_KEY` | 한 쌍이다. 하나만 채우거나 형식이 틀리거나 한 쌍이 아니면 서버가 시작할 때 멈추고, 둘 다 비우면 푸시만 꺼진다. |
| `VAPID_SUBJECT` | 푸시 서비스가 문제를 알릴 연락처(`mailto:` 또는 `https://`)다. 비우면 `https://na-wa.cloud`를 쓴다. |

키를 만드는 방법은 `.env.example`에 있다. **키를 바꾸면 이미 구독한 기기는 새 키로 다시
구독하기 전까지 푸시를 받지 못한다** — 구독은 만들 때 쓴 공개키에 묶인다.

### 화면의 동작

- 알림 목록 맨 위의 카드에서 켜고 끈다. 권한 요청은 사용자의 클릭에서 곧바로 이어져야 해서(Safari
  요구) 공개키는 카드가 보이는 동안 미리 받아 둔다.
- iOS 사파리 탭에는 푸시 API가 없다. 홈 화면에 추가한 앱(iOS 16.4 이상)에서만 열리므로 카드가
  추가 방법을 안내한다.
- **로그인한 뒤 처음 보호 화면에 들어올 때** 이 기기의 구독을 다시 등록한다. 같은 기기에 다른
  계정이 로그인했다면 서버가 소유자를 옮긴다. 화면 언어를 바꿀 때도 다시 등록한다.
- **로그아웃 전에** 이 기기의 구독을 서버에서 지운다. 인증이 살아 있는 동안에만 가능해서
  로그아웃 요청보다 먼저이고, 3초를 넘기거나 실패해도 로그아웃은 막지 않는다. 브라우저 구독은
  남겨 두어 같은 기기로 다시 로그인하면 권한을 다시 묻지 않는다.
- 서비스 워커(`frontend/src/sw.ts`)는 앱이 닫혀 있든 열려 있든 푸시를 알림으로 띄우고, 누르면
  `/settlements/{id}`로 이동한다. 열린 창에는 메시지를 보내 알림·정산 쿼리를 바로 다시 받게 한다.

### 저장

`push_subscriptions`(V22)에 기기마다 한 행이다. 해지하거나 푸시 서비스가 끝났다고 알리면 행을
지운다(소프트 삭제가 아니다) — 잃는 이력이 없고 알림 자체는 `notifications`에 남아 있다.

`endpoint`는 대소문자를 구분해 비교한다(V23, `utf8mb4_bin`). endpoint는 푸시 서비스가 기기마다
정해 준 토큰이 든 주소이고 토큰은 대소문자를 구분하는데, 기본 collation은 이를 같은 값으로 봐서
대소문자만 다른 두 기기의 등록이 서로의 행을 덮어쓸 수 있었다.

## 미납 리마인더

정산을 요청받고도 오래 내지 않은 구성원에게 서버가 같은 알림 목록으로 다시 알려 준다. 요청 알림
한 번이 전부이면 받는 사람이 놓쳤을 때 돈을 받을 사람이 직접 독촉해야 한다.

리마인더는 정산 상태가 바뀐 일이 아니라 **시간이 지나서 생기는 일**이라 정산 서비스의 이벤트를
거치지 않는다. 스케줄러가 대상을 골라 알림을 적고, 푸시는 [웹 푸시](#웹-푸시)와 같은 경로로
나간다. 푸시가 꺼져 있거나 받지 못해도 알림 목록에는 남는다.

### 정책 (초안)

| 항목 | 값 | 상수 (`SettlementReminderServiceImpl`) |
| --- | --- | --- |
| 첫 발송 | 요청한 날로부터 3일 뒤 | `FIRST_REMINDER_AFTER_DAYS` |
| 재발송 간격 | 3일 | `REMINDER_INTERVAL_DAYS` |
| 횟수 상한 | 3회 | `MAX_REMINDERS` |

팀이 숫자를 확정하면 상수만 바꾼다. 한 묶음의 크기(`CHUNK_SIZE`, 100)는 정책이 아니라 트랜잭션
크기다.

**날짜 단위로 센다.** "72시간이 지났나"로 비교하면 매일 같은 시각에 도는 실행이 밀리초 차이로
하루씩 밀린다. 오늘 날짜에서 (N-1)일 전 자정을 기준으로 삼으면 요청한 날의 몇 시에 만들었든
N일 뒤 첫 실행부터 대상이 된다. 10일 오후 2시에 요청한 정산은 13일 실행에서 첫 리마인더를
받고, 16일과 19일에 받은 뒤 더는 받지 않는다. 같은 날에는 몇 번을 돌려도 결과가 같다. 오늘
날짜는 앱(JVM, `TZ=Asia/Seoul`)이 `LocalDateTime.now()`로 정하며 DB 시계를 쓰지 않는다.

기준이 되는 정산의 만든 시각(`settlements.created_at`)은 앱이 넘긴 값이다
([정산 API 계약](SETTLEMENT.md#정산-목록-응답의-시각)). DB 시계에 맡기면 DB와 앱의 시간대가
어긋난 만큼 첫 리마인더가 밀린다.

### 누구에게 보내는가

아래를 모두 만족하는 구성원이다.

- 아직 안 냈다(`request_status = 'PENDING'`, 지워지지 않음).
- 정산이 요청 상태이고 지워지지 않았다(`REQUESTED`).
- 받는 회원이 `ACTIVE`이고 지워지지 않았다.
- 지금까지 보낸 횟수(`reminder_count`)가 상한 미만이다.
- 한 번도 안 보냈거나(`last_reminded_at`이 비어 있음), 마지막 리마인더가 간격보다 오래됐다.

원결제자 본인(`NOT_REQUESTED`), 이미 낸 사람, 완료된 정산, 탈퇴·정지·삭제된 회원에게는 보내지
않는다. 약속 참가 상태(약속에서 나갔는지)는 보지 않는다. 나가도 이미 진 빚은 그대로이고 정산은
그 사람이 낼 때까지 끝나지 않으므로, 아직 안 냈다면 알려 줄 사람이다
([정산 API 계약](SETTLEMENT.md#정산-상세의-납부-현황)과 같은 이유다).

알림은 구성원마다 하나다. 받는 사람은 그 구성원이고, `actorName`은 돈을 받을 원결제자, `amount`는
그 사람이 낼 몫이며 통화는 원거래에서 온다. 정산 요청 알림과 담는 값이 같다.

### 언제 도는가

`SettlementReminderScheduler`가 서울 시각 10시부터 20시까지 **매시 정각**(크론
`0 0 10-20 * * *`)에 실행을 시작한다. 밤에는 보내지 않는다.

한 실행은 **50분**을 넘기지 않는다. 묶음마다 푸시 대기열 때문에 최대 30초를 기다릴 수 있어서, 밀린
대상이 많은 날 푸시까지 느리면 실행이 몇 시간 이어져 20시 실행이 밤에도 보내게 된다. 50분이 지나면
다음 묶음을 읽지 않고 멈추고, 남은 사람은 다음 정각 실행이 이어받는다. 20시 실행은 20시 50분
무렵에 끝나고, 그때 남은 사람은 다음 날 10시에 받는다.

날짜 단위 기준이라 같은 날 첫 실행이 대상을 모두 처리하고, 이후 실행은 할 일이 없다. 매시 도는
것은 앞 실행이 중간에 멈췄을 때 다음 정각이 **이어서 끝내기** 위해서다. 처리한 사람은 발송
기록 때문에 조건에서 빠지므로 재시작을 따로 만들 필요가 없다.

스케줄러 스레드는 일을 넘기기만 한다. 이 앱의 `@Scheduled` 작업은 스레드 하나를 같이 쓰는데
(`RootConfig`에 스케줄러 빈이 없다), 리마인더를 거기서 돌리면 미납이 많은 날 보증금 정산
처리(60초 주기)와 약속 상태 전이가 그만큼 밀린다. 그래서 전용 실행기(스레드 이름 `reminder-`,
스레드 1개, 대기열 없음)에 넘긴다. 앞 실행이 아직 돌고 있으면 이번 정각은 쌓지 않고 건너뛰며
"이전 미납 리마인더 실행이 아직 진행 중"이라는 로그만 남긴다. 건너뛰어도 잃는 것이 없다. 다음
정각이 남은 사람부터 이어받는다.

### 중복 없이, 도중에 멈춰도 이어서

한 번의 실행이 한 트랜잭션에 몰리지 않도록 100명씩 끊어 처리한다.

```text
실행 → 후보 번호 100개 읽기(잠그지 않음)
     → 묶음 트랜잭션: 같은 조건으로 다시 읽으며 잠금 → 발송 기록 → 알림 적재 → 커밋
     → 커밋된 알림으로 푸시 요청 → 다음 묶음(커서 = 방금 고른 마지막 번호)
```

- **두 번 읽는다.** 잠그지 않고 번호만 고른 뒤, 트랜잭션 안에서 같은 조건으로 다시 읽으며
  잠근다. 그 사이에 낸 사람이나 다른 서버가 먼저 처리한 사람은 다시 읽을 때 걸러진다. 두 쿼리는
  조건 조각을 공유해서 한쪽만 어긋나지 않는다.
- **선점과 적재는 한 트랜잭션이다.** 발송 기록(`last_reminded_at`, `reminder_count`)과 알림
  INSERT가 함께 커밋되거나 함께 사라진다. "기록은 있는데 알림은 없는" 사람이 생기면 다음
  실행이 그 사람을 이미 받은 것으로 보고 영영 건너뛴다. 푸시는 **커밋된 뒤에만** 요청하므로
  묶음이 롤백돼도 이미 나간 푸시가 남지 않는다.
- **서버가 여러 대여도 같은 사람에게 두 번 가지 않는다.** 실행 단위 잠금은 두지 않는다. 행 잠금
  (`FOR UPDATE OF sm SKIP LOCKED`)과 다시 읽는 조건으로 충분하다. 다른 서버가 잡은 행은 기다리지
  않고 건너뛰어 그쪽 몫이 되고, 이미 처리된 행은 조건에서 빠진다.
- **지급과 겹쳐도 교착하지 않는다.** 같은 쿼리가 정산 행에도 공유 잠금(`FOR SHARE OF s SKIP
  LOCKED`)을 잡는다. 알림을 INSERT할 때 외래키 검사가 정산 행에 공유 잠금을 요구하는데, 지급은
  정산 행을 먼저 잡고 구성원 행을 잡는다. 리마인더가 구성원 행만 쥔 채 정산 행을 기다리면 같은
  사람의 지급과 서로를 기다리는 교착이 난다. 이 잠금을 빼면 그 교착이 나는 것을 테스트로
  재현했다(`SettlementReminderWriterIntegrationTest`).
- **`READ COMMITTED`로 읽는다.** `REPEATABLE READ`의 잠금 읽기는 훑은 범위에 갭 잠금을 잡아 그
  사이에 새 정산을 만드는 INSERT를 막을 수 있다.
- **한 건이 묶음을 막지 않는다.** 묶음이 실패하면 그 번호들을 한 건씩 각자 트랜잭션으로 다시
  처리하고, 그래도 실패한 건만 건너뛰어 센다. 일시적인 잠금 오류도 이 재시도로 풀린다. 건너뛴
  건은 발송 기록이 없으므로 다음 정각이 다시 시도한다. 로그에는 구성원 번호와 예외 종류만
  남긴다. `RuntimeException`만 잡고 `Error`는 잡지 않는다. 실행이 멈추고, 다시 부르면 남은
  사람부터 이어진다.
- **푸시 속도를 조절한다.** 푸시 대기열(스레드 4개, 대기열 200)은 가득 차면 새 작업을 버린다.
  리마인더가 그것을 채우면 실시간 정산 알림 푸시가 밀려 버려지므로, 다음 묶음을 읽기 전에
  대기열이 (용량 200 − 묶음 100 − 실시간 몫 50) = 50 이하로 내려올 때까지 기다린다. 최대 30초이고,
  넘으면 그냥 진행한다. 푸시는 최선 노력이고 놓친 알림은 폴링이 메운다. 푸시가 꺼져 있으면
  대기열이 늘 비어서 기다리지 않는다.
- **실행 이력 표는 두지 않는다.** 실행 요약(묶음 수·알림 수·건너뜀·소요 시간)을 반환값과
  로그(`미납 리마인더 실행을 마쳤습니다. chunks=…, reminded=…, skipped=…, elapsedMillis=…`)로만
  남긴다. 실행 이력을 DB에 남기는 표가 생기면 그때 붙인다.

### 처음 배포할 때

`settlement_members`에 `last_reminded_at`·`reminder_count`를 되살린 V24 이전에 쌓인 미납
구성원은 횟수 0, 마지막 시각 없음으로 시작한다. 요청한 지 3일이 지난 미납 구성원은 **첫 실행에서
한꺼번에** 첫 리마인더 대상이 된다. 이것은 정책대로의 동작이다. 한 번에 몰리는 것이 부담이면
배포 전에 오래된 구성원의 `last_reminded_at`을 날짜별로 나눠 채워 두면 간격 규칙이 분산한다.
이 저장소에는 그 보정 SQL을 두지 않았다.

### 화면

- 알림 목록과 기기 알림이 같은 문구(`notification.item.SETTLEMENT_REMINDER`)를 4개 언어로 보여
  준다. 서버는 문장이 아니라 값을 보내고 문구는 화면이 만든다.
- 누르면 정산 요청 알림과 같이 해당 정산 상세(`/settlements/{id}?origin=notifications&side=received`)로
  이동한다. 낼 사람이 받는 알림이라 뒤로 가면 "낼 정산" 쪽 목록이 열린다.
- **누른 것만으로 읽음이 되지는 않는다.** 푸시를 눌러도 읽음 처리하지 않고, 알림 목록에서 항목을
  눌렀을 때 그 알림 하나만 읽음이 된다.

### 대량 처리 측정

미납이 많아도 한 번의 실행이 묶음 단위로 끝나고, 약속한 성질이 그 규모에서도 지켜지는지
재 두었다. 테스트는 `SettlementReminderScaleTest`이고 **CI에서 돌지 않는다.**
`RUN_REMINDER_SCALE_TEST=true`일 때만 돌고, 10만 건을 시드하므로 일회용 DB에서만 돌린다.

| 항목 | 값 |
| --- | --- |
| 측정 시점 | PR #601 (rebase 전 측정) |
| 환경 | 로컬 Docker의 MySQL 8.4.13(기본 설정, DB 시간대 UTC), macOS, JDK 17.0.12, 프로세서 10개, 연결 풀 8 |
| 시드 | 미납 대상 10만 건(정산 1만 개 × 10명), 이미 낸 10만 건, 요청한 지 3일이 안 된 5천 건, 탈퇴 회원 5백 건 |
| 불량 | 알림 적재 직전에 예외를 던지게 한 20건 |

| 실행 | 묶음 | 알림 | 건너뜀 | 시간 |
| --- | ---: | ---: | ---: | ---: |
| 1회 실행 (불량 20건) | 1,000 | 99,980 | 20 | 10.1초 |
| 같은 실행을 다시 | 1 | 0 | 20 | 0.11초 |
| 불량이 풀린 뒤 다시 | 1 | 20 | 0 | 0.07초 |
| 500번째 묶음에서 강제 중단 | 499 | 49,900 | - | 3.1초 |
| 중단 뒤 재개 | 501 | 50,100 | 0 | 3.0초 |
| 동시 2회 (A / B) | 1,000 / 999 | 49,981 / 50,019 | 0 | 두 실행이 끝날 때까지 4.0초 |

불량이 없는 구간은 한 실행이 초당 약 1.6만 건(재개 구간)을 처리했다. 불량 20건이 든 첫 실행이 더
오래 걸린 것은 그 묶음 20개가 통째로 롤백된 뒤 100명씩 한 건씩 다시 돌았기 때문이다.

확인한 것은 모두 테스트가 단정한다.

- 대상 10만 건 가운데 정상 99,980건은 정확히 한 번(`reminder_count = 1`, 알림 1건)씩 받았고,
  같은 사람이 알림을 두 번 받은 경우가 없다. 불량 20건은 기록도 알림도 없다.
- 요청한 지 3일이 안 된 정산과 탈퇴 회원은 한 번도 건드려지지 않았다.
- 푸시 요청 수는 커밋된 알림 수와 같다(99,980). 롤백된 묶음의 푸시는 나가지 않았다.
- 같은 실행을 다시 돌리면 불량 외에는 할 일이 없다(알림 0건). 불량이 풀린 뒤 다음 실행이 그
  20건을 처리한다.
- 500번째 묶음에서 멈춘 뒤 다시 돌리면 남은 5만 100건만 처리하고, 합치면 정확히 한 번씩이다.
  멈춘 묶음은 기록도 알림도 남기지 않고 롤백됐다.
- 동시에 두 번 돌려도 합쳐 정확히 한 번씩이고 건너뜀이 없다.

`EXPLAIN`도 같은 테스트가 매퍼가 만드는 SQL 그대로 확인한다.

| 쿼리 | 구성원(`sm`) | 나머지 테이블 |
| --- | --- | --- |
| 후보 읽기 `findCandidateIds` | 미납 인덱스 `idx_settlement_members_request_status`로 번호 순서 범위 읽기(`Using index condition`), 정렬·임시 테이블 없음 | 기본키 조회 |
| 잠금 읽기 `lockTargets` | 받은 번호 100개를 기본키 범위로 읽기 | 기본키 조회 |

**측정이 바로잡은 것.** 처음 측정(미납 10만 건만 시드, 이미 낸 행 없음)에서 후보 읽기가 정산 표
전체를 먼저 훑고(`s`: `type=ALL`, 약 1만 행) 임시 테이블과 정렬(`Using temporary`,
`Using filesort`)로 번호 순서를 만들었다. 묶음마다 그 일을 되풀이해 1회 실행이 80.6초, 동시 2회가
128.5초 걸렸다. `STRAIGHT_JOIN`으로 읽는 순서를 구성원 → 정산 → 약속 참가 → 회원으로 고정하자
나머지가 기본키 조회가 되었다. 이어서 이미 낸 구성원 10만 건을 더해도 옵티마이저가 기본키 범위를
고르는 것을 보고 `FORCE INDEX`로 미납 인덱스를 못 박았다. 위 표가 그 뒤의 값이다. 두 힌트를
빼면 쿼리가 조용히 느려지므로 매퍼 XML에 이유를 적어 두었고, 이 테스트가 `EXPLAIN`으로 다시
확인한다.

**한계.** 로컬 컨테이너 하나에서 다른 트래픽 없이 잰 값이라 운영 환경의 절대 시간이 아니다.
"묶음 단위로 끝난다", "정확히 한 번"과 같은 성질을 규모에서 확인하고 변경 전후를 견주는 용도다.
푸시는 요청 수만 세었다. 실제 발송과 대기열 속도 조절은 단위 테스트가 확인한다.

다시 재려면 일회용 MySQL 8.4를 띄우고 **팀이 쓰는 DB가 아닌** 곳을 가리킨다.

```shell
cd backend
RUN_REMINDER_SCALE_TEST=true \
DATABASE_DRIVER=com.mysql.cj.jdbc.Driver \
DATABASE_URL="jdbc:mysql://127.0.0.1:3306/nawa_scale?useSSL=false&allowPublicKeyRetrieval=true&serverTimezone=Asia/Seoul" \
DATABASE_USERNAME=<일회용 DB 계정> DATABASE_PASSWORD=<일회용 DB 비밀번호> \
./gradlew test --no-daemon --tests '*SettlementReminderScaleTest'
```

결과는 `backend/build/reminder-scale-report.txt`에 남는다. 시드는 테스트가 끝나면 지운다(번호가
10억 이상인 행만).

## 아직 없는 것

정산 밖 도메인의 알림, 종류별 수신 설정, 지운 알림의 자동 정리(보관 기간), 푸시를 못 받은
기기의 재시도, 로그인 세션에 묶은 구독 정리(위 "로그아웃 버튼을 거치지 않고 세션이 끝나면"),
404·410 밖의 반복 거절(403 등)을 횟수로 세어 정리하는 정책, 한 회원의 기기별 발송을 병렬로
나누는 것. 필요해지면 후속 이슈로 다룬다.

마지막 둘은 일부러 미뤘다. 반복 거절은 서버의 VAPID 설정이 틀렸을 때도 인증 거절이 올 수 있어, 거절만
보고 지우면 멀쩡한 구독을 한꺼번에 잃을 수 있고 실패 횟수를 저장할 컬럼과 기준이 필요하다. 키를
바꾼 경우는 위의 자동 다시 구독이 예전 행을 지운다.
발송은 전용 스레드풀(4개·대기열 200)이 곧 역압이라, 기기별 요청을 비동기로 나누면 그 한도가
동시에 날아가는 요청 수로 옮겨 가 부하 시험(시나리오 4)이 재는 한계가 달라진다. 한 회원의 기기
수는 20대로 막아 두었으므로, 한 알림이 스레드 하나를 붙잡는 시간은 기기마다 연결 3초 + 응답
5초가 모두 걸리는 최악의 경우에도 20대 × 8초다.
정산 밖 도메인의 알림(보증금 등), 종류별·사용자별 수신 설정과 방해 금지 시간, 지운 알림의 자동
정리(보관 기간), 푸시를 못 받은 기기의 재시도와 VAPID 키를 바꿨을 때의 자동 재구독. 리마인더는
낮에만 도는 것이 스케줄의 제한일 뿐 사용자별 설정이 아니고, 실행 이력을 DB에 남기는 표도 아직
없다(요약은 반환값과 로그에만 있다). 필요해지면 후속 이슈로 다룬다.
